# New Feature

Read [commit-attribution.md](../../references/commit-attribution.md) for message formatting and change origins, within this skill's existing effect boundaries.

Create or revise exactly one feature epic in an existing project's canonical roadmap. Do not implement or publish. Staging and committing approved documents require the separate delivery-input boundary in the shared integration contract.

On a pre-execution route from `$aquarium:epic-handler` or `$aquarium:epic-squad`, continue in the same conversation for the exact repository, roadmap, and existing epic ID. Preserve the existing epic ID. Keep the task membership unless the user explicitly approves a task-structure change in this design workflow. Create or revise one dossier only when the shared threshold requires it; update its TODO index entry and roadmap link as needed. Resolve any identified semantic gap in its canonical owner. A material change to the epic's goal or scope needs an explicit user decision in this design workflow. Use the selected Design Procedure, independent execution envelope, provider authority, scoped document-write authority and final applied-content acceptance, and delivery-input commit boundary. After successful design delivery, report the applied paths, committed revision when required, remaining worktree state, and an exact new-conversation request naming the repository root, canonical roadmap, epic ID, and the original collaboration owner. A Squad caller also carries its exact mode, supplied profiles and role omissions through [the caller/return contract](../../references/epic-squad-execution.md#design-continuation-and-explicit-opt-out); use `target.design.caller` in the ordinary Design assignment and preserve separate Design write authority, final content acceptance and delivery-input commit boundaries. If a required commit remains unauthorized or a blocker remains, report that boundary as the next action instead of claiming execution is ready.

Always read [evidence-residency.md](../../references/evidence-residency.md), then read [ouroboros-integration.md](../../references/ouroboros-integration.md), [documentation-governance.md](../../references/documentation-governance.md), and [epic-execution-sot.md](../../references/epic-execution-sot.md), and follow [adaptive Design execution](../../references/adaptive-execution.md#design-entrypoints).

Resolve the target roadmap's recorded identity contract before allocating an epic or task ID. Establish repository authority, current architecture and behavior, epic identity, user outcome, non-goals, dependencies, migration needs, failure behavior, rollout boundary, and acceptance evidence.

After the approved envelope, use installed upstream `$interview`, `$pm`, or `$seed` only as needed. Before `$pm`, apply the shared [PM file and clipboard boundary](../../references/ouroboros-integration.md#pm-files-and-clipboard): disclose draft writes and obtain authority to replace the clipboard. Produce one coherent epic with ordered work units and explicit ownership. Apply the shared execution-SOT threshold; create or revise one scope-local dossier only when required, otherwise keep the complete execution contract in the roadmap and at most two requirement-bearing canonical documents.

Run upstream `$qa`, adjudicate the draft, recheck current target snapshots and apply the documents within the invocation or approved envelope scope. Do not require a patch artifact, displayed diff or separate application approval. Report actual file links, decisions and validation so the user can review the working tree. Apply requested corrections within the same scope and rerun affected QA and validation. Obtain final acceptance of the applied content before claiming design completion or preparing its delivery-input commit. End with the epic identity, applied paths, validation, and implementation blockers.

Apply the shared QA outcome mapping and [delivery-input commit boundary](../../references/ouroboros-integration.md#commit-approved-delivery-input). Report whether documents are applied or committed before naming the next explicit workflow.

## Ordinary native orchestration

Follow [Design and diagnosis orchestration](../../references/design-diagnosis-orchestration.md) for ordinary v3 native assignments, grouped independent assessments, original evidence and recovery. Preserve upstream leaf and effect boundaries. New scoped-capable Design bindings use the document-write and applied-content review contract; retained bindings keep their original exact-diff approval contract. No native history, role snapshot or configuration qualification is required. Existing formal snapshots retain their original contracts; source updates do not authorize managed-file rollout.

## Adaptive Design execution

Before Podway discovery or source preparation, branch on explicit Podway opt-out and, for `new-project`, non-Git scope. Continue ordinary Executor/Evaluator work with scoped document application and final applied-content review, with Podway inapplicable; do not initialize Git or Podway. On the native path, follow [adaptive Design execution](../../references/adaptive-execution.md#design-entrypoints) for actual fit, exact admission and same-session recovery. Prefer adequate unchanged Design sources and preserve their first due grouped assessment. Keep this entrypoint's artifacts, upstream leaves, selected reviews and effect authority.


For fresh scoped work, select a scoped-capable Design source. A retained exact-diff source is not adequate for that application model. If no qualified scoped source is available, report the needed released managed update through dev-setup; never patch managed files or ask for a diff approval as a workaround. Existing sessions continue under their retained contract.
