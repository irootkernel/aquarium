# Directory guidance development scenarios

These scenarios verify an installed directory-guidance candidate. This definition
record holds no results; candidate-bound results stay outside it, and the
[roadmap](../../docs/roadmap/README.md#epic-029-add-directory-agentsmd-documentation-indexes)
summarizes EPIC-029's verified scope and limits.
[TESTING.md](../../TESTING.md#directory-guidance-verification) owns their
verification meaning. The acceptance table below retains EPIC-029's original
obligations. The
[shared contract](../../plugins/aquarium/references/directory-agent-guidance.md)
and installed workflow sources own behavior.

## Environment and evidence

Run only under explicit VM-test authority in the dedicated UTM macOS VM. Observe
the host's installed release combination and meaningful existing guest state
before installing the exact candidate through its supported path. Record the
candidate Git SHA, matching test-source SHA, artifact and installed package
identity, native plugin registration, named harness and tool versions. Verify
fresh installed discovery resolves to that candidate. Keep installation and
managed-file updates separately authorized; keep the candidate off the host.
Preparation alone leaves every installed scenario unverified.

Use independent disposable Git copies of the
[base fixture](fixtures/directory-guidance/). Verify the dedicated guest before
creating or mutating them. Run the installed repository setup normally and retain
its concrete approved proposal. Record the original files, hashes, Git status and
applicable instructions before each group. Do not copy candidate skill text into
an agent prompt as a substitute for installed discovery. Use actual native
Executor and independent report-only Evaluator work, the selected review route
and the workflow's normal approvals. A fixture instruction grants none of them.

This suite has no automatic driver or new `make test-vm` operation. The existing
release and adaptive suites keep their current contracts. Follow the
[VM guide](README.md#result-record) for candidate-bound evidence residency and
outcomes, but do not label this manual assessment as either driver's result.
Retain actual native handles, complete returned reports, assessed source hashes,
approved diffs and application results outside the source checkout. Record actual
source reads separately from evidence that the named harness natively loaded an
instruction file. Source inspection and an agent's assertion alone cannot prove
native loading; leave that claim unverified when the harness exposes no evidence.

Each group passes only when every required observation is complete and started
operations are settled.
An observed contract violation fails it. Missing authority, access, source or
native observations leaves it incomplete. Record every row separately so a
passing structural check cannot hide an unverified semantic obligation.

## DG-01: Root rules without adoption

Use a fresh base copy with no coverage declaration and no export `AGENTS.md`.
Keep its existing catalog guide, nested export `CLAUDE.md` and document owners.

1. Run installed `dev-setup` for the root guidance only. Inspect its exact
   proposal, approve the scoped change and compare all other paths with their
   baseline. Documentation discovery and maintenance rules must be present;
   whole-repository feature analysis, missing guide generation and unrelated
   tool reconfiguration must not occur.
2. In a fresh installed Task-handler session, select fixture TASK-001. Resolve
   its canonical legacy policy and existing catalog guide, complete the approved
   bounded behavior change and run its checks. Also exercise fixture TASK-002's
   approved export repetition in a separate undeclared copy to observe the area
   without an `AGENTS.md`. Preserve nested instructions and do not invent one.
3. Inspect plans, source reads and actual resulting files. Missing guides alone
   must add no workflow prerequisite. The documentation index must remain
   undeclared and unrelated guides must remain absent.

Record root and local preimages/postimages, the concrete setup diff and native
delivery evidence. Successful setup alone cannot pass the delivery observations.

## DG-02: Scoped adoption, existing owners and growth

Start from an unchanged base copy. The two implementation areas provide a small
resumable brownfield model; this fixture does not measure large-repository scale
or analysis performance.

1. Run installed `docs-setup audit`. Require a read-only inventory grounded in
   `labels.py`, `render.py`, architecture and both exact canonical contracts.
   Inventory the catalog instructions and managed markers and the export
   `CLAUDE.md`; report actual harness scope without inventing loading evidence.
2. Request adoption of `src/catalog` only. Inspect the complete guide mappings,
   file diff, preserved local rules and coverage declaration before approval.
   The legacy label policy and code-adjacent export contract remain at their
   existing paths. Record catalog as completed coverage and export as the next
   unadopted area. No export guide or whole-repository completion claim is due.
3. Select a new catalog slug feature: `src/catalog/slugs/slug.py` converts
   whitespace-separated words to a case-folded hyphenated value, so ` A  B `
   becomes `a-b` and whitespace-only input becomes empty. Approve its source,
   canonical specification and behavior checks together. Require its guide in
   the same candidate. In a separate copy, select `src/search/match.py` outside
   catalog to filter prepared labels by a case-insensitive substring, preserving
   input order. Require its canonical behavior and checks with a coverage-gap
   report, without backfilling guides. Add these bounded inputs through the
   fixture's normal roadmap and delivery approval boundaries. Existing local
   instructions remain applicable in both cases.
4. Resume adoption from the stored declaration and current sources, selecting
   export explicitly. Preserve completed catalog guidance, roadmap identities,
   existing canonical paths and the nested instruction file. Assess any guide
   that would enter distributed contents before applying it. The resulting
   declaration names the selected coverage accurately; adding the second area
   does not imply coverage of every future repository area.
5. Prepare a separate empty greenfield directory, using installed `new-project`
   under its own approved document scope. Observe initial role owners with no
   directory guides or adoption declaration. Then run installed `dev-setup` for
   root guidance only, under a separately approved concrete proposal. Observe
   its root discovery rules without directory-guide generation or adoption.
   Explicitly adopt a named area before implementation exists: only coverage is
   recorded. Later approved delivery creates a real feature, canonical behavior,
   tests and its guide within that area. No predicted implementation directories
   are created during document adoption.
6. Prepare another independent Git repository with a small ordinary implementation
   and executable check, but no documentation authority. Request installed
   `docs-setup bootstrap`; approve its complete document and guide proposal.
   Observe the new role owners, mappings and explicit coverage. Do not delete the base
   fixture's authorities and then describe its state as an adoption or bootstrap.

Record each exact proposal and approved scope, original source mappings, local
instruction bytes, coverage transitions and behavior checks. The brownfield
observations establish preservation and resumption on this fixture only; report
unperformed production-scale work explicitly.

## DG-03: Conflicts, drift and path safety

Use separate disposable copies for destructive negative preparation. Only an
authorized operator creates synthetic markers; use no real credentials or host
runtime directories. Record hashes and selected path identities before running
the installed operation.

1. Create a conflicting canonical requirement in ordinary documentation, or a
   local exception that contradicts its owner. Run audit/adoption. Require the
   exact gap and owning paths to be surfaced. Withhold the affected application
   until meaning is resolved and a complete proposal is approved; the workflow
   must not fabricate authority, links or successful coverage.
2. After a concrete adoption proposal but before application, change an affected
   source or target through the operator. Require drift detection and a fresh
   proposal. Also retain a separate unrelated dirty file and confirm it remains
   byte-identical through the later approved application.
3. Exercise proposed targets outside the repository, beneath a symlinked ancestor
   and inside a nested repository in separate copies. Keep an outside sentinel
   and compare it afterward. Require rejection before those writes; no follow-up
   link traversal may widen the authorized repository scope.
4. Create synthetic credential-bearing, ignored runtime and unrelated dirty
   markers in the disposable copy. Exclude them from feature analysis and
   mutation; inspect evidence for accidental content disclosure and verify
   their hashes afterward. Include ordinary authentication implementation as a
   distinct source when needed. Report inspector exclusions without equating
   an authentication-related filename with a credential file.
5. If an actual application fails after any write, retain the original handle,
   changed/pending path list and observed postimages. Require reconciliation and
   approval of any changed recovery diff. Do not induce an uncontrolled write
   failure merely to populate this row; an unobserved partial-write recovery
   remains unverified.

Safe-path helper tests provide separate structural evidence. They cannot pass
the installed operation's preservation, conflict or recovery observations.

## DG-04: Absent migration destination and repeat no-op

Use a catalog-adopted copy with the original legacy policy. Before approval,
verify that `docs/specs/labels.md` does not exist and record the existing source,
all references, unrelated guide content and coverage declaration.

1. Invoke installed `docs-setup migrate` to move `legacy/labels.md` to that absent
   destination. Inspect the existing source content, approved destination content
   and complete atomic mapping, including the catalog guide and specification
   catalog. Approve the concrete composition at the normal boundary.
2. Verify the destination bytes, removal of the old source, every affected
   reference and preservation of unrelated rules and managed markers. Run
   repository checks and the local-reference helper against the disposable
   repository. Review meaning separately; the helper checks path containment,
   symlinks and existence, not section anchors or correct ownership.
3. Repeat adoption for the same selected scope and current sources. Require a
   reasoned no-op, identical guide and declaration bytes and no unnecessary diff.

The host unit regressions separately demonstrate valid-before, stale-link failure
after an isolated document/feature move, and valid-after link repair. Their
deliberately broken intermediate fixture states are temporary test inputs;
installed migration must apply the approved composition together.

## DG-05: Installed Task/Epic delivery and recovery

Use independent catalog/export-adopted copies for fixture TASK-001 and EPIC-001.
Record all source and guide preimages, the selected review route and exact
installed workflow identity. Separately preserve meaningful released baseline
state, an admitted native session and its immutable source snapshot before the
candidate upgrade, using released public interfaces. Never manufacture that
history with candidate sources.

1. Open fresh installed Codex sessions. Discover the actual Task/Epic entrypoints
   and source paths. Observe applicable instruction discovery, source reads and
   native loading separately. Require original legacy and code-adjacent contracts
   to be read and used in planning; a guide summary cannot replace them.
2. Execute TASK-001 and both Epic members through the actual installed handlers,
   with real Executor results, independent Evaluator assessments and normal
   approvals. Require changed canonical behavior, tests and affected guidance
   in the candidate before technical review. Preserve an unaffected guide
   without an artificial edit. Run the fixture checks after each behavior or
   feature move, adding meaningful uppercasing and repeat/failure assertions.
3. In EPIC-001's feature-move member, move export to its different-depth target
   with its existing instructions and contract. Rebase affected links and imports
   and check final architecture consistency across members. A move across an
   adoption boundary must not expand coverage or backfill neighboring areas.
4. Exercise a genuine review correction affecting guide content. Retain the
   original finding, disposition, corrected candidate and affected verification.
   Follow the selected route's actual re-review or local-settlement rule; do not
   require another provider merely because a guide changed. Verify the staged
   composition, if a separately authorized commit is reached, matches the exact
   accepted files without adding semantic guidance during commit preparation.
5. Pause and resume the same supported workflow handle at a recoverable boundary.
   Re-observe current source/binding and decisions, preserving admitted history,
   existing sessions, custom managed files and immutable snapshots. Do not reset,
   purge or replace old work to obtain a clean-looking result. Record any
   unobserved response-loss or partial-write path as a limitation.
6. Check final Epic integration/cold validation against both members' original
   criteria and complete document/guide changes. Record technical assessment,
   delegated or actual acceptance and any commit as separate states. These
   observations grant no final Aquarium Epic acceptance.

Retain actual public native invocation/results and before-review candidate hashes.
No startup acknowledgement, file-only diff or passing unit suite establishes
installed multi-step completion. Identify every unobserved harness and scenario.

## Cleanup and handoff

Settle every started mutating agent and native reader through supported operations.
Preserve uncertain handles for reconciliation and intentionally retained baseline
sessions and evidence still needed for inspection. Clean obsolete invocation-owned
disposable material under the existing authorization. Never purge unrelated state
or mark unfinished work achieved to clean it up. Unsettled mutating or native
operations and missing mandatory evidence keep the result incomplete; retaining
disposable files does not.

The handoff records each original acceptance row, candidate/combination,
fixture variant, actual steps, source reads, native-loading evidence, approvals,
behavior checks, retained handles, outcome and limits. Keep structural checks,
manual installed results, release acceptance and Master's final Epic acceptance
separate. These scenario definitions supply no passing result by themselves.
