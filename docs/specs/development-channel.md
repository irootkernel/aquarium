# Development Channel Specification

The explicit-only `$aquarium:aquarium-dev` workflow manages one canonical local-`main` checkout per supported project on Darwin arm64. Supported producers are Aquarium, Podway, Mulgae, Gaori, Sanho, and Dolgorae. Dolgorae remains unenrolled until its repository commits and registers an approved producer generation; production review paths continue to use only the verified globally installed release binary.

Diagnosis is read-only. Enrollment metadata, a native hook marker, an initial or recovery build, and installation of the user-local launcher are separate effects with separate approvals. All Aquarium-owned development state lives below `~/.aquarium-dev/`; `~/.aquarium/` is reserved for production use.

Every producer owns `make aquarium-dev-describe` and `make aquarium-dev-build AQUARIUM_DEV_OUTPUT=<absolute-empty-directory>`. A build admits only a clean checkout whose `HEAD` is local `main`, consumes committed bytes, emits one exact-SHA manifest, and writes only into the supplied staging directory. Aquarium's producer packages one Codex plugin artifact from committed bytes. Foreground tools retain the frozen v1 executable contract. The generic v2 managed-service contract packages a development-safe public command and producer-owned controller inside one immutable bundle; Podway is its first required adopter.

The manager validates the declared identity, version, entrypoints, path containment, and canonical checksum before immutable promotion. Foreground commands atomically advance `current/<project-id>`. A managed-service build advances `pending/<project-id>` and preserves the active command/controller/service pair until a separately approved exact-token controller apply reports the target generation ready. Busy services defer activation. Every consumer holds a shared artifact lease; managed-service consumers also hold the service-generation lock. Cleanup requires exclusive access and never removes current or pending generations.

The separately approved `~/.local/bin/aquarium-dev` launcher prefers a supported tool's exact `~/.aquarium-dev/bin` generation. Only an absent foreground tool resolves from the caller's original global `PATH`, excluding both Aquarium state roots. A managed service requires strict controller readiness and matching active generation and never falls back to production. Unknown commands and invalid development state fail closed. The child receives `~/.aquarium-dev/bin` first in `PATH`, while the caller's environment and any existing `CODEX_HOME` remain unchanged. The launcher does not create a Codex home, perform authentication, install a plugin, or configure MCP servers.

Aquarium's service controller protocol provides read-only `status` and `plan` operations plus a separately approved, exact-token `apply`. Aquarium owns generic runtime roots, locks, validation, and generation selection only. Each producer owns its LaunchAgent, daemon arguments, sockets, registries, logs, recovery, and tool-specific state transitions.

Host-local development evidence is neither stable installation nor release or distribution proof. Exact executable behavior is owned by the [`aquarium-dev` skill](../../plugins/aquarium/skills/aquarium-dev/SKILL.md), its [development contract](../../plugins/aquarium/skills/aquarium-dev/references/development-contract.md), the [manager](../../plugins/aquarium/skills/aquarium-dev/scripts/dev_manager.py), the [launcher](../../plugins/aquarium/skills/aquarium-dev/scripts/aquarium_dev_launcher.py), the [Aquarium producer](../../plugins/aquarium/skills/aquarium-dev/scripts/build_aquarium_artifact.py), and the repository [Makefile](../../Makefile).
