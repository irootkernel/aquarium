## Bounded procedure: Sorage protocol and common packet contract

### Step 1: Milestone M1 pre-send packet freeze (`TASK-091`)

Before allocating any remaining-scope Sorage request in `TASK-091`, freeze this runbook (`docs/ops/integrated-tool-rollout.md` indexed in [`docs/ops/README.md`](README.md)) and the exact request drafts retained by the active execution handoff. Pass Milestone `M1` review (`TE`, two non-authoring independent `TO`s for elevated `TASK-091`, and scoped `EE`, followed by `CO` confirmation) before `CO` sends the Podway request.

### Step 2: Recipient resolution and single request allocation (`CO` only)

1. Resolve the exact recipient Project ID through `use-sorage`; never guess a slug from a product name.
2. Construct the producer request packet containing:
   - Stable logical correlation key `aquarium/EPIC-032/<TASK-ID>/<product>-rollout/v1` (for Podway, `aquarium/EPIC-032/TASK-091/podway-rollout/v1`).
   - Frozen authority references and their digests. Retain the immutable request-document SHA-256 alongside its exact body and native receipt; do not try to embed a document's own hash recursively in that document.
   - Common Haepari v0.1.0 execution, profile, skill-tree, migration, manual-completion, and cleanup obligations plus the producer's specific clause from this runbook.
   - Reused early-cleanup references where applicable, requesting only missing verification scope or corrections.
   - Permitted effect boundaries (guest VM candidate installation only; no host mutation or automatic release).
3. Before allocation, retain the nonempty native idempotency key, exact recipient/title/body and flags, Installation identity, and cwd/sender binding. Allocate once and preserve the real receipt (`handoffId`, `revision`, `rowVersion`, `requestId`) in native Sorage and the retained execution handoff.

### Step 3: External producer execution and correlated completion return

1. Hold the active Aquarium Task at `deliver-work` using supported native waiting semantics.
2. The producer allocates its own local roadmap/task IDs. Accepting the request Handoff acknowledges scope; it does not complete the Aquarium Task.
3. After satisfying the required implementation and verification criteria with actual evidence, including applicable reused results, the producer sends a separate correlated completion-report Handoff to Aquarium referencing the logical correlation key, native request ID and revision, immutable request digest, and accepted scope. The producer never edits Aquarium's sender-owned request or managed Vault.

### Step 4: Frozen required producer return fields (`rollout-5`)

Every producer completion Handoff must include all of the following fields:

1. Producer identity: Resolved producer Project/repository identity and producer-owned local Epic and Task IDs.
2. Source and test commits: Exact source, candidate, and test commit SHAs.
3. Installation unit and skill-tree provenance: Exact binary, archive, or package version and SHA-256 digest, plus complete skill-tree provenance (`git rev-parse HEAD:<skill-dir>`, per-file digests for every file in each shipped skill directory, and fresh-session skill discovery verification).
4. Haepari runtime identity: Haepari v0.1.0 executable, runner, and capability identity; shared `utm-macos` outer-boundary VM occupancy serialization; and explicit separation of pre-submission request inputs from returned `job_id`, `job_revision`, exported evidence, and cleanup handoff.
5. Profile digests: Starting and target profile identities and SHA-256 digests resolved before admission. Never relabel a `v0.2.14` profile as `v0.2.16`. Any candidate using an API beyond the frozen Haepari contract is a dependency change that must be resolved before acceptance.
6. Suite Job references and observations: Per-suite Haepari `job_id`, `job_revision`, terminal status, and actual automatic and manual (`awaiting_manual` evidence staging and cleanup/inventory before `manual complete`) observations. Keep native Job, review, evidence, cleanup, capacity, and assessment outcomes separate.
7. Migration and regression evidence: Verification against meaningful prior-version state (workspace identity, configuration, history, retry state, active-work obligations, or Vault/session records as applicable) and regression results.
8. Manual verification and gaps: Actual manual hands-on or CLI/GUI observations and any explicit manual gaps.
9. Cleanup and restored guest inventory: Proof that automatic workloads finished recipe cleanup before exit, manual workloads completed cleanup and inventory while `awaiting_manual` before `manual complete` collection, and the guest VM matches the declared reusable inventory. Cleanup need not reinstall the prior release: retain the tested combination where the owning scenario requires it.
10. Obsolete source removal: Exact commits and paths removing `aquarium-dev`-specific source integration.
11. Host detachment vs. shared infrastructure: Separately evidenced detachment or proven absence of exclusive producer-owned legacy hooks, callers, and services, kept distinct from producer-reported inspection-time observations and from shared `~/.aquarium-dev/` infrastructure retained for `EPIC-033` (`TASK-101`).
12. Release status and limits: Released vs. unreleased status and remaining runtime, provider, or backend limits.
13. Evidence-backed `not_applicable`: Source-backed `not_applicable` entries where a prior release, native skill, or legacy hook never existed. Never invent `use-gul`, `use-seongge`, or `use-gaebokchi` to satisfy a template.
14. Mulgae advisory-lock fields (`TASK-092` only): Released CLI/skill identity, the shared CLI/MCP acquisition path, lock Installation, request, grant and generation references, and original native run and publication results. Include renewal, contention, replay, cancellation/race, borrower, terminal-release, renewal-loss and partial-role evidence and the observed advisory limits required below.

### Step 5: Correction loop and acceptance ordering (`grant-current` before Handoff acceptance)

1. If the producer's completion Handoff is incomplete or inconsistent, `CO` requests bounded corrections through the supported native Sorage review/revision protocol (`changes_requested` or revision-fenced review comment with fresh read `revision` and `rowVersion` fences) and re-verifies the updated return revision. Never edit producer source from Aquarium.
2. Prepare all required bounded non-sensitive tracked evidence and record changes before freezing the candidate. Obtain Task-result coverage from `TE`, the independent non-authoring `TO` panel and scoped `EE`, complete `current-composition`, and record `CO` product review and exact candidate acceptance. Reuse applicable milestone judgments and test receipts; run only checks due for the actual delta. For this document change, the focused checks are `ruby tests/validate.rb` and `git --no-pager diff --check`.
3. At `record-acceptance`, verify that this exact acceptance remains current and the unconsumed member commit grant (`grant-current`) is valid before accepting the Sorage Handoff.
4. `CO` reads fresh Sorage `revision` and `rowVersion` fences, accepts the completed producer return Handoff once, and retains the native receipt in its native/local recovery owner. Complete `closeout` and `$aquarium:task-commit` on the accepted candidate before advancing. A required post-acceptance tracked record delta needs exact acceptance of its final bytes under the applicable correction/reuse rules before commit; it does not authorize repeating Handoff acceptance. Never claim an acceptance receipt before the native operation returns it.
